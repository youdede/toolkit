# Protected branch guard for Claude Code

This project-scoped `PreToolUse` hook protects `main`, `master`, and the locally discoverable repository-default branch. It uses bounded, non-shell Git subprocesses to identify the repository, current branch, and `refs/remotes/origin/HEAD`. It blocks native `Write`, `Edit`, `MultiEdit`, and `NotebookEdit` calls while the current branch is protected.

For Bash calls, the hook reads the command through the shared item parser without executing expansions. It recognizes literal wrapper layers, static shell `-c` payloads, protected-branch history mutations, protected local-ref deletion, protected remote-ref deletion, and direct pushes whose destination is protected. A bare `git push` (or `git push <remote>` to the same remote) is resolved through Git's own `@{push}` and blocked only when that destination is protected; when Git cannot name a single destination, the push is refused. Configured Git aliases are expanded once and re-inspected. A refspec without an explicit destination is refused when its remote has a `remote.<name>.push` mapping, because the mapping can redirect it. `git send-pack` and `git http-push` are refused, and so are command runners (`xargs`, `find -exec`, `parallel`, `watch`) that start a relevant Git subcommand. A branch or HEAD change earlier in the same command (`git switch`, `git checkout <branch>`, `git checkout -b`, `git rebase <upstream> <branch>`, `git branch -m`, `git symbolic-ref HEAD`, `gh pr checkout`) makes later Git commands count against the branch HEAD may be on. Inside an `&&` chain after the change (pipelines included), the change is certain, so only the new branch counts, and a bare `git push` uses that branch's own `@{push}`, resolved before the command runs. After `;`, `||`, `&`, a newline, or a switch piped into another command, the original branch stays a candidate too, because a failed switch leaves HEAD on it. After a `git config` or `git branch -u` write, a bare `git push` no longer trusts any earlier `@{push}` and is refused. A push with an explicit refspec that does not name `HEAD` stays inspectable. Aliases and `remote.<name>.push` written by `git config` earlier in the same command are applied. `git fetch` and `git pull` with a refspec that writes another branch into a protected branch, or merges another branch into the current protected branch, are blocked; refreshing a protected branch from the same-named branch of a named remote is allowed. `git worktree add -b/-B` with a protected name is blocked. All Git subprocesses share one 8-second budget, below the adapter timeout. A malformed or dynamically constructed relevant command fails closed. Detached HEAD and verified non-repository directories do not block native edits; an unborn protected branch does.

A program the command runs but does not contain (`bash -c "$CMD"`, `curl … | sh`, `eval "$(tool)"`, `python3 -c "$CODE"`) is judged by shell-command-guard; this hook refuses one only when its text names `git push`, `git commit`, `git merge`, `git reset`, `git rebase`, `git branch -f` and similar phrases.

## Refusals and limits

- The hook does not create a feature branch, stash work, checkpoint, commit, merge, rebase, delete, or push.
- It has no project-writable bypass and does not treat a command comment or environment variable as approval.
- It does not call a network service, inspect remote branch-protection settings, or claim to replace server-side rules.
- It does not interpret arbitrary scripts as hidden Git operations; a dynamic executable that can be Git running a mutation, and relevant scope changes (including `GIT_DIR`, `GIT_WORK_TREE`, and `GIT_CONFIG*` prefixes), are refused instead.
- Shell aliases (`!…`) and aliases of aliases are blocked as uninspectable.
- A switch followed by `;`, `||`, or `&` may have failed, so the earlier branch stays a candidate: `git switch feature; git push` on `main` is refused, while `git switch feature && git push` is judged on `feature`.
- Branch changes made by other tools or scripts (for example `git stash branch`, git-town, a custom script) are not recognized; `git reset` and `git branch -f` are not treated as branch changes because they do not move HEAD to another branch.
- It does not cover filesystem mutations performed by arbitrary Bash commands, MCP tools, IDE extensions, or other processes.

Examples it refuses include a native edit on `main`, `git commit` on the default branch, `git branch -D main`, `git update-ref -d refs/heads/main`, `git push origin feature:main`, and a static wrapped equivalent. It allows read-only Git commands, a direct push to an unprotected feature branch, a bare `git push` whose configured destination is unprotected, branch switching, recovery-only `--abort`/`--quit` operations, and `git push --dry-run`.

Works with shell-command-guard. Alone, this hook judges the commands it can read in the call. It cannot see inside a command that hides what it runs (`bash -c "$X"`, `curl … | sh`, `eval "$(tool)"`); shell-command-guard, installed with it by default, is the hook that stops those. The installer asks first in a terminal (default yes) and installs it with a notice elsewhere; `youdede-toolkit add protected-branch-guard --no-prerequisites` installs this hook alone, and `youdede-toolkit add shell-command-guard` adds it later.

Retained false positives (hook-design 4.3), each refused on purpose:

- An opaque executable (`$"x" …`, translated by the locale at run time) is uninspectable when its words can be one of the commands this hook protects.
